# 华为畅享 20 Plus：移植思路

## 1. 先保留能驱动硬件的底座

目标为 FRL / MT6853，历史环境为厂商 4.14.141+ 内核与 Ubuntu 24.04 ARM64 用户空间。并非重新实现整套手机硬件驱动：复用兼容厂商内核、设备树和必要二进制运行时，再为 Linux 用户空间补齐启动、服务、设备访问和生命周期管理。

应先明确分区布局、内核能力、设备节点和启动入口，再分层验证串口、存储、基础用户空间、网络、电源、显示和触摸。设备身份/校准分区应留在各自设备上，不能拿另一台手机的备份替代。

## 2. 启动链与故障保底

```text
原设备引导链 / 厂商内核
  → 自定义 ramdisk / PID 1
  → USB 串口恢复入口、存储检查
  → F2FS userdata 内的 ext4 rootfs 文件
  → 根文件系统几何、UUID、阶段标志与 payload 校验
  → 原生 frl-init / runit
  → 网络、电源、终端、按需本地显示
```

串口恢复必须在根文件系统接管之前可用。校验失败时停留恢复模式，而不是继续执行不确定的启动脚本。串口会话要正确处理标准输入输出、session、控制终端、进程身份和退出清理。

rootfs-v3 是历史约 4 GiB 的 ext4 根镜像；用户数据位于独立数据区域。这里的 4 GiB 不是手机总存储容量。更新运行系统后，不能再把初始整镜像 SHA 当作永久不可变标识；应结合阶段状态及不可变 payload 文件清单管理。详见 [DEPLOYMENT.md](DEPLOYMENT.md)。

## 3. 复用厂商服务，但隔离写入与生命周期

部分硬件依赖厂商服务和 Android/Bionic ABI。Linux 侧用最小所需运行环境、只读厂商挂载及 RAM 内临时目录运行它们，不直接把 Android 的全部启动服务搬过来。

对服务保留 PID 与启动时间等身份检查，避免 PID 重用误杀；对挂载验证路径、类型、来源和只读属性。停止、超时和重启都要有明确所有权，不用 `killall` 或 lazy unmount 掩盖残留。

## 4. GPU 与屏幕是两层

```text
Python：采样、输入、布局、三角形/字形缓存
  → 原生 Mali GLES renderer
  → ION / DMA-BUF 缓冲
  → DRM/KMS page flip
  → DSI 屏幕
```

Cairo/Pango 只生成缓存字形遮罩，不对每一帧整屏软件光栅化。画面无变化时不持续提交绘制，因此 Mali 可以显示 0% 或断电休眠；显示控制器仍能扫描已有帧缓冲。

DRM master、CRTC、framebuffer、缓冲引用和厂商运行时必须按顺序接管和释放。`active framebuffer exists` 表示选中的 CRTC 仍有 framebuffer，不足以单独确定占用者。应核对旧桌面、启动画面、异常退出和服务顺序；不能简单删掉断言。详见 [显示生命周期](DISPLAY-LIFECYCLE.md)。

## 5. 服务端与本地面板分离

界面采样和耗时操作分开：Wi-Fi 先显示已有列表，后台扫描；应用/服务操作走受限后台接口。进程操作保留身份检查及重要进程影响确认。自动熄屏是显示省电，不是需要密码的安全锁屏。

成熟组件能用就复用：runit 管生命周期，SSH 做远程管理，tmux 保持终端；扩展监控可独立采用 Glances。不要把所有系统管理逻辑都写进绘图循环。

## 6. 跨设备移植需要重做哪些部分

- 引导入口、分区布局、设备树和内核配置。
- GPU ABI、缓冲分配/同步、显示扫描输出和触摸事件协议。
- 背光、电源键、充电、电池、Wi-Fi 与厂商服务适配。
- 校验基线、恢复入口、停机清理与冷启动测试。

界面和部分纯 Python 逻辑可复用；FRL 的硬编码设备路径、固定 SHA、DRM 流程和亮度量程不能直接套到 K20P 或其他机型。
